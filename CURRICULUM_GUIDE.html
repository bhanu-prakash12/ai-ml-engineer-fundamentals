01 — Python Fundamentals for ML Engineering

Learning objectives

By the end of this topic you can: - Use Python's core data structures (list/tuple/set/dict) correctly, including when mutability matters. - Write comprehensions, generators, and decorators instead of reaching for manual loops/boilerplate. - Model data with classes, dataclasses, and magic methods the way ML codebases do (configs, batches, records). - Reason about asyncio vs threading vs multiprocessing and know why the GIL makes that choice non-obvious. - Use pathlib, regex, logging, and json/csv the way production ML pipelines do.

Why it matters

Every ML framework (PyTorch Dataset/DataLoader, Hugging Face datasets, scikit-learn pipelines) is Python wrapped around C/CUDA. If you're shaky on generators, decorators, or *args/**kwargs, reading framework source code — or debugging why your training loop silently drops the last batch — becomes much harder than it needs to be.

Prerequisites

None — this is the starting point of the curriculum.

Core concepts

  • Collections: list (ordered, mutable) vs tuple (ordered, immutable) vs set (unordered, unique) vs dict (key→value). Indexing/slicing (a[1:3], a[::-1]) and the mutability trap (a = b = []).
  • Comprehensions: [x**2 for x in xs if x > 0] — the idiomatic replacement for build-and-append loops; same syntax for sets/dicts.
  • Functions: positional/keyword args, *args/**kwargs for variadic signatures (every nn.Module.forward(*args, **kwargs) relies on this), lambda for throwaway callables, map/filter/zip/enumerate for functional-style iteration.
  • OOP: classes, __init__, inheritance vs composition ("has-a" vs "is-a" — prefer composition for ML model components), @dataclass for data-holding classes without boilerplate, magic methods (__repr__, __len__, __getitem__, __iter__) — these are exactly what a PyTorch Dataset needs.
  • Iterators & generators: the iterator protocol (__iter__/__next__), yield for lazy, memory-efficient sequences — the same idea behind streaming datasets.
  • Decorators: functions that wrap functions (@property, @staticmethod, custom timing/caching decorators) — the same mechanism behind @torch.no_grad().
  • Context managers: with blocks and __enter__/__exit__ — the same mechanism behind with torch.no_grad():.
  • Exceptions: try/except/finally, custom exception classes, when to catch vs let propagate.
  • Typing: type hints (list[int], Optional[str], Callable) for self-documenting, tool-checkable code.
  • Concurrency: the GIL means CPU-bound Python threads don't parallelize — use multiprocessing for CPU-bound work (e.g. parallel data preprocessing) and asyncio/threading for I/O-bound work (e.g. concurrent API calls).

Key takeaways

  • Comprehensions and generators are not just "shorter loops" — generators give you O(1) memory for arbitrarily large sequences, which is why streaming datasets use them.
  • *args/**kwargs is how every flexible ML API (optimizers, forward(), callbacks) stays extensible without breaking signatures.
  • The GIL means threads don't help CPU-bound Python work — know when to reach for multiprocessing instead.
  • Magic methods are the contract PyTorch Dataset and many other framework base classes expect you to implement.

Common mistakes

  • Using a mutable default argument (def f(x=[])) — the same list is reused across calls.
  • Confusing is (identity) with == (equality).
  • Writing CPU-bound parallel code with threading and being confused why it isn't faster (the GIL).
  • Materializing a huge list with a list comprehension when a generator expression would do.
  • Catching bare except: and silently swallowing real bugs.

02 — NumPy: Thinking in Shapes

Learning objectives

By the end of this topic you can: - Create and inspect ndarrays (shape, dtype, ndim). - Index/slice/reshape/transpose arrays and predict the resulting shape before running code. - Explain and apply broadcasting rules. - Use vectorized operations and boolean masking instead of Python loops. - Compute dot products, matrix multiplication, and reductions, and reason about tensor shapes through a mock "mini neural network layer" computation.

Why it matters

Every tensor library (PyTorch, TensorFlow, JAX) uses NumPy's mental model: shape, dtype, strides, broadcasting. If you can predict X @ W + b's output shape without running it, you can read any model's forward() method. If you can't, every shape-mismatch error becomes a guessing game.

Prerequisites

01_python — comfort with Python functions and basic data structures.

Core concepts

  • ndarray: NumPy's core data structure — a typed, fixed-shape, contiguous (by default) block of memory.
  • shape/ndim/dtype: shape is a tuple describing size along each axis; dtype controls memory layout and numeric precision (float32 vs float64 matters a lot for ML).
  • Indexing & slicing: basic slicing (a[1:3]), boolean masking (a[a > 0]), fancy indexing (a[[0, 2]]).
  • reshape/transpose/squeeze/expand_dims: changing how the same data is viewed without copying (usually).
  • concatenate/stack: joining arrays along existing vs new axes.
  • Broadcasting: NumPy's rule for applying an operation between arrays of different (but compatible) shapes without explicit loops.
  • Vectorization: expressing an operation over a whole array at once — orders of magnitude faster than a Python for loop, because it drops into compiled C code.
  • dot product / matrix multiplication: np.dot, @, np.matmul — the core operation of every linear layer.
  • Reductions: sum/mean/max/argmax along an axis — which axis gets reduced is a constant source of bugs.
  • Tensor-shape reasoning: given X: (batch, in_features) and W: (in_features, out_features), X @ W has shape (batch, out_features) — this is the whole vocabulary of a neural network layer.

Important APIs / functions

np.array, .shape, .ndim, .dtype, .reshape, .T/np.transpose, np.squeeze, np.expand_dims, np.concatenate, np.stack, broadcasting (elementwise +/* between different shapes), boolean masking (a[a > 0]), np.dot/@/np.matmul, .sum/.mean/.max/.argmax(axis=...).

Key takeaways

  • Always know the shape of every array you're working with — print it or assert it.
  • Broadcasting lets (32, 10) + (10,) work without a loop — the smaller array is "stretched" along compatible axes.
  • Vectorized NumPy code is fast because it avoids per-element Python overhead, not because of magic.
  • axis=0 reduces rows (collapses down each column); axis=1 reduces columns (collapses across each row) — this trips up almost everyone at least once.

Common mistakes

  • Confusing axis=0 and axis=1 in a reduction.
  • Assuming .reshape() always copies (it often returns a view — mutating the result can mutate the original).
  • Adding arrays with incompatible shapes and being surprised by a ValueError instead of understanding broadcasting rules.
  • Using float64 everywhere without realizing GPU-bound deep learning code typically wants float32.
  • Writing a Python for loop over array elements instead of a vectorized operation.

Debugging 1. a.reshape(3, 4) raises a ValueError on a 10-element array — why, and how do you fix it? 2. A broadcasting operation silently produces a much larger array than expected (e.g. (32, 1) + (1, 10) → (32, 10)) — why did that happen, and was it intended?

Real-world engineering 1. 03 — Data Libraries: Pandas, Polars, PyArrow

Learning objectives

By the end of this topic you can: - Load, filter, sort, clean, and aggregate tabular data with Pandas. - Express the same operations with Polars' expression API, including lazy execution. - Understand Arrow's columnar memory format and read/write Parquet with PyArrow. - Know when to reach for each library.

Why it matters

Almost every ML pipeline starts with tabular data: labeled examples, logs, or metadata joined against features. Pandas is the lingua franca for exploration; Polars is increasingly used for speed and memory efficiency on larger-than-RAM data via lazy execution; Arrow/Parquet is the columnar interchange format behind Hugging Face datasets, Spark, and most data lakes.

Prerequisites

02_numpy — a DataFrame column is backed by array-like shape thinking.

Core concepts

Pandas

  • Series (1D, labeled) and DataFrame (2D, labeled rows/columns).
  • Loading data (read_csv, read_json), filtering (df[df.col > 0]), sorting (sort_values).
  • Missing values (isna, fillna, dropna) and duplicates (duplicated, drop_duplicates).
  • groupby + aggregation (.agg, .mean(), .sum()).
  • merge/join (SQL-style joins) and concat (stacking).
  • pivot/melt (reshaping wide ↔ long).
  • .apply/.map (row/element-wise transforms — a last resort after vectorized ops).

Polars

  • DataFrame, the expression API (pl.col("x") > 0), which Polars can optimize and parallelize.
  • Lazy execution: LazyFrame builds a query plan (.lazy() ... .collect()) instead of executing eagerly, letting Polars push down filters/projections.
  • Joins, aggregations, and streaming (processing data larger than RAM in chunks).

PyArrow

  • The Arrow columnar in-memory format — the same layout Pandas 2.x, Polars, and datasets can all share without copying.
  • Reading/writing Parquet (pyarrow.parquet) — the standard columnar on-disk format for ML datasets.

Arrow memory layout .-> D D --> E[Parquet file: columnar, compressed, shared format] E --> F[Hugging Face datasets / training pipeline]

Important APIs / functions

Pandas: pd.read_csv, pd.DataFrame, boolean filtering, .sort_values, .isna/.fillna/.dropna, .duplicated/.drop_duplicates, .groupby().agg, pd.merge, pd.concat, .pivot/.melt, .apply. Polars: pl.DataFrame, pl.col, .filter, .select, .group_by().agg, .lazy()/.collect(), .join. PyArrow: pyarrow.Table.from_pandas, pyarrow.parquet.write_table/read_table.

Key takeaways

  • Pandas optimizes for ergonomics and the richest ecosystem; Polars optimizes for speed/memory via lazy, parallel execution; Arrow/Parquet is the shared columnar format that makes moving between them (and into datasets) cheap.
  • groupby + agg is the single most common tabular ML-prep operation (e.g. aggregating events per user).
  • Lazy execution (.lazy()...collect()) lets Polars see the whole query before running it, enabling optimizations eager execution can't do.
  • Parquet is columnar and compressed — much smaller and faster to read a subset of columns from than CSV.

Common mistakes

  • Using .apply() with a Python function when a vectorized Pandas/Polars expression would do the same thing 10-100x faster.
  • Forgetting reset_index() after a groupby and being confused by a MultiIndex.
  • Not checking for duplicate rows before aggregating, silently double-counting.
  • Treating Polars eager and lazy APIs as interchangeable without realizing lazy defers execution until .collect().

04 — Datasets: Design Principles + Hugging Face `datasets`

Learning objectives

By the end of this topic you can: - Explain samples/features/labels and why train/validation/test splits exist. - Identify and fix common dataset problems: missing values, outliers, duplicates, imbalance, and leakage. - Normalize/standardize numeric features and encode categorical ones. - Use Hugging Face datasets' Dataset/DatasetDict, map/filter/select/shuffle/train_test_split, batched processing, and streaming.

Why it matters

Model quality is bounded by dataset quality far more often than by architecture choice. Leakage (information from validation/test leaking into training) silently inflates reported accuracy and is one of the most common real-world ML bugs. Hugging Face datasets is the standard interface for dataset manipulation you'll reuse directly when fine-tuning LLMs later in this workspace's llm-fine-tuning/ curriculum.

Prerequisites

03_data_libraries — datasets is built on Arrow, covered there.

Core concepts

  • Samples / features / labels: a sample is one row/example; features are its inputs; a label is what you're predicting (supervised learning only).
  • Train / validation / test split: train to fit, validation to tune/select, test to report a final, unbiased estimate — never tune based on test performance.
  • Structured vs unstructured data: tabular/structured (rows+columns) vs text/image/audio (unstructured, needs featurization).
  • Cleaning: missing values (drop vs impute), outliers (cap/remove/investigate), duplicates (can cause train/test leakage if not removed before splitting).
  • Imbalance: when one class dominates — accuracy becomes misleading; needs resampling, class weights, or different metrics (see Day 2's evaluation topic).
  • Leakage: any case where information not available at prediction time (or from the test set) influences training — e.g. normalizing using statistics computed over the entire dataset before splitting, or duplicate rows split across train and test.
  • Normalization/standardization: scaling numeric features (min-max to [0,1], or z-score to mean 0/std 1) — fit the scaler on train only, then apply to val/test.
  • Encoding: turning categories into numbers (one-hot, label/ordinal encoding) since models need numeric input.

Hugging Face datasets

  • load_dataset — loads a dataset (from the Hub or local files) as Arrow-backed Dataset/DatasetDict.
  • .map() — apply a function to every example (optionally batched=True for speed).
  • .filter() — keep only examples matching a predicate.
  • .select() — take a specific set of row indices.
  • .shuffle() / .train_test_split() — randomize order / split into train+test with reproducible seeds.
  • .remove_columns() — drop columns no longer needed after preprocessing.
  • Streaming: load_dataset(..., streaming=True) yields an IterableDataset that never loads the whole thing into memory — the dataset-level analog of the generators from 01_python.
flowchart LR A[Raw data] --> B[Clean: missing values, outliers, duplicates] B --> C[Split: train / validation / test] C --> D[Fit scalers/encoders on TRAIN ONLY] D --> E[Apply to val/test] E --> F[HF Dataset: map/filter/select/shuffle] F --> G[Batched or streaming processing] G --> H[Ready for a model's DataLoader]

Important APIs / functions

datasets.load_dataset, datasets.Dataset, datasets.DatasetDict, .map, .filter, .select, .shuffle, .train_test_split, .remove_columns, batched=True, streaming=True.

Key takeaways

  • Fit any data-dependent transform (scaler, encoder, vocabulary) on the training split only, then apply it unchanged to validation/test.
  • Deduplicate before splitting, or duplicates can land in both train and test, leaking information.
  • Class imbalance doesn't go away by ignoring it — accuracy on an imbalanced dataset can look great while the model learns to always predict the majority class.
  • datasets.Dataset is Arrow-backed, so .map(batched=True) is fast and streaming works on data too large for memory — the same ideas as 03_data_libraries.

Common mistakes

  • Normalizing/standardizing using statistics from the whole dataset before splitting (leakage).
  • Shuffling before splitting without a fixed seed, making results non-reproducible.
  • Treating accuracy as sufficient on an imbalanced dataset.
  • Calling .map() without batched=True on a large dataset when the function could easily be vectorized over a batch.

Debugging 1. A model gets 99% validation accuracy but performs terribly in production — what dataset issue would you check first? 2. After splitting, you realize duplicate rows exist in both train and test — what's the fix, and does it require re-splitting?

05 — ML Mathematics: Linear Algebra, Probability/Statistics, Calculus

Learning objectives

By the end of this topic you can: - Explain scalars/vectors/matrices/tensors and compute dot products, matrix multiplication, transpose, and norms. - State what eigenvalues/eigenvectors and SVD represent at an intuitive level and where they show up in ML (PCA, dimensionality reduction). - Apply Bayes' theorem and reason about expected value, variance, covariance, and correlation. - Compute a derivative, partial derivative, and gradient by hand for a small function, and connect that to gradient descent.

Why it matters

Every ML algorithm is linear algebra (data representation and transformations), probability (uncertainty, loss functions like cross-entropy, Bayesian models), and calculus (how a model learns, via gradients). Backpropagation in 16_backpropagation on Day 3 is nothing more than the chain rule applied repeatedly — if that's solid here, backprop won't feel like magic there.

Prerequisites

02_numpy — every concept here is implemented with NumPy.

Core concepts

Linear algebra

  • Scalars/vectors/matrices/tensors: 0D/1D/2D/N-D numeric objects.
  • Dot product: u · v = Σ uᵢvᵢ — a measure of alignment between two vectors; the core operation inside every linear layer.
  • Matrix multiplication: composing linear transformations; (m,n) @ (n,p) -> (m,p).
  • Transpose: flipping rows/columns; used constantly to make shapes line up for matmul.
  • Norms: ‖v‖₂ (Euclidean length) — used in regularization (L2) and distance metrics.
  • Eigenvalues/eigenvectors: directions a matrix only scales (doesn't rotate) — the basis for PCA.
  • SVD (concept): decomposes any matrix into rotation-scale-rotation (U Σ Vᵗ) — underlies PCA, dimensionality reduction, and recommender systems.

Probability & statistics

  • Probability, conditional probability, Bayes' theorem: P(A|B) = P(B|A)P(A) / P(B) — the basis of generative models and many evaluation metrics.
  • Random variables & distributions: a random variable maps outcomes to numbers; common distributions (normal, Bernoulli, binomial) model different kinds of uncertainty.
  • Expected value, variance, covariance, correlation: the mean, spread, and joint-spread of a distribution — correlation is covariance normalized to [-1, 1].
  • Sampling: drawing data from a distribution — the basis of train/test splitting, bootstrapping, and stochastic gradient descent's "stochastic" part.

Calculus

  • Derivative: instantaneous rate of change — "if I nudge the input, how much does the output move?"
  • Partial derivative: derivative with respect to one variable, holding others fixed — needed once a function has more than one input (every model parameter).
  • Gradient: the vector of all partial derivatives — points in the direction of steepest increase.
  • Chain rule: d/dx f(g(x)) = f'(g(x)) · g'(x) — the single rule that makes backpropagation possible.
  • Gradient descent: repeatedly stepping against the gradient to minimize a function — θ ← θ - η∇L(θ).
flowchart LR A[Scalars/vectors/matrices] --> B[Dot product & matmul] B --> C[Norms, eigenvalues/eigenvectors, SVD] D[Probability & Bayes] --> E[Random variables, E/Var/Cov/Corr] F[Derivative] --> G[Partial derivative & gradient] G --> H[Chain rule] H --> I[Gradient descent: θ ← θ - η∇L] C -.-> J[PCA / dimensionality reduction] E -.-> K[Loss functions, evaluation metrics] I --> L[Day 3: backpropagation is the chain rule, repeated]

06 — ML Fundamentals

Learning objectives

By the end of this topic you can: - Distinguish supervised, unsupervised, semi-supervised, self-supervised, and reinforcement learning, with an example of each. - Define features, labels, parameters, and hyperparameters precisely enough to not confuse them in an interview. - Explain training vs inference and why they use the model differently. - Explain generalization and model capacity, and why neither "more capacity" nor "less capacity" is universally better.

Why it matters

This is the vocabulary the rest of Day 2 and Day 3 assume. Every later topic ("regularization", "hyperparameter tuning", "overfitting") is meaningless without a precise handle on parameters vs hyperparameters and training vs inference.

Prerequisites

Day 1 complete, especially 05_ml_mathematics (gradient descent) and 04_datasets (splits).

Core concepts

  • Supervised learning: learn a mapping from features to known labels (regression, classification).
  • Unsupervised learning: find structure in unlabeled data (clustering, dimensionality reduction).
  • Semi-supervised learning: a small amount of labeled data plus a large amount of unlabeled data.
  • Self-supervised learning: labels are derived automatically from the data itself (e.g. predict a masked word) — the basis of most modern LLM pretraining.
  • Reinforcement learning: an agent learns by interacting with an environment and receiving rewards, not from a fixed labeled dataset.
  • Features: the inputs a model sees. Labels: the supervised target. Parameters: values the model learns from data (e.g. weights w, bias b). Hyperparameters: values a human (or a search) sets before training that control how learning happens (e.g. learning rate, number of trees, k in k-NN).
  • Training vs inference: training updates parameters using labeled data and a loss function; inference uses the already-trained, now-fixed parameters to make predictions on new data.
  • Generalization: how well a model performs on data it did not train on — the entire point of ML.
  • Model capacity: how complex a function class a model can represent — too little capacity underfits; too much, without enough data/regularization, overfits (formalized in 11_generalization).

07 — Regression

Learning objectives

By the end of this topic you can: - Derive and implement linear and multiple linear regression from scratch with NumPy (least squares and gradient descent). - Fit the same models with scikit-learn and get matching results. - Compute and interpret MSE, MAE, RMSE, and R².

Why it matters

Linear regression is the simplest supervised model and the cleanest way to see the full ML pipeline (fit → predict → evaluate) without an opaque algorithm in the middle. Every regression metric here (MSE/MAE/RMSE/R²) reappears throughout Day 2 and in real evaluation dashboards.

Prerequisites

06_ml_fundamentals, Day 1's 05_ml_mathematics (gradient descent, calculus).

Core concepts

  • Linear regression: ŷ = wx + b (one feature) or ŷ = Xw + b (many features) — fit the line/hyperplane that minimizes squared error.
  • Multiple regression: more than one feature; X becomes a matrix, w becomes a vector.
  • Least squares (closed-form): w = (XᵗX)⁻¹Xᵗy — directly solves for the optimal weights when XᵗX is invertible.
  • Gradient descent: iteratively approaches the same optimum (useful when the closed-form solution doesn't scale or doesn't exist, e.g. non-invertible XᵗX).
  • MSE / MAE / RMSE / R²: MSE punishes large errors more (squared); MAE is robust to outliers (absolute); RMSE puts the error back in the original units; R² is the fraction of variance explained (1.0 = perfect, 0.0 = no better than predicting the mean).
flowchart LR A[Data: X, y] --> B["Closed-form: w = (XᵗX)⁻¹Xᵗy"] A --> C[Gradient descent: iteratively minimize MSE] B --> D["Predictions ŷ = Xw + b"] C --> D D --> E["Evaluate: MSE / MAE / RMSE / R²"] E -.connects to.-> F[12_ml_evaluation: the same metrics, formalized]

Important APIs / functions

08 — Classification

Learning objectives

By the end of this topic you can: - Distinguish binary, multiclass, and multilabel classification. - Fit and reason about logistic regression, k-NN, decision trees, random forests, gradient boosting, XGBoost, LightGBM, SVM, and Naive Bayes. - For each algorithm, state what it does, how it works, when to use it, its strengths/weaknesses, and common failure cases.

Why it matters

Classification is the most common supervised-learning task in production ML (spam detection, fraud, churn, intent classification). Knowing when to reach for logistic regression vs a gradient-boosted tree vs an SVM — and why — is a staple interview topic and a real engineering decision with cost/latency/interpretability tradeoffs.

Prerequisites

07_regression (the same fit/predict/evaluate pipeline, now with a categorical target).

Core concepts

  • Binary / multiclass / multilabel: binary = 2 classes; multiclass = >2 mutually exclusive classes; multilabel = each sample can belong to multiple classes simultaneously.
  • Logistic regression: linear regression's output passed through a sigmoid, trained with log-loss — what: a linear decision boundary with probabilistic output. How: gradient descent on cross-entropy loss. When: interpretable baseline, linearly (or near-linearly) separable data. Strengths: fast, interpretable, probabilistic output. Weaknesses: can't capture non-linear boundaries without manual feature engineering. Failure case: XOR-like data that isn't linearly separable.
  • k-NN: classify by majority vote among the k nearest training points. When: small datasets, non-linear boundaries, no training phase needed. Weaknesses: slow at inference (must scan training data), sensitive to feature scaling and the curse of dimensionality.
  • Decision tree: recursively split on the feature/threshold that best separates classes. Strengths: interpretable, handles non-linear boundaries and mixed feature types. Weaknesses: prone to overfitting if unconstrained (unlimited depth).
  • Random forest: an ensemble of decision trees, each trained on a bootstrap sample with random feature subsets, averaged/voted. Strengths: much less overfitting than a single tree, good default performance. Weaknesses: less interpretable, slower, larger memory footprint.
  • Gradient boosting: builds trees sequentially, each correcting the previous ensemble's errors (fits the residual/gradient of the loss). Strengths: often the best tabular-data performance. Weaknesses: more hyperparameters to tune, easier to overfit than random forest if not careful, slower to train (sequential).
  • XGBoost / LightGBM: optimized, production-grade gradient boosting implementations — XGBoost is depth-wise with strong regularization controls; LightGBM grows leaf-wise and uses histogram-based splits for speed on large datasets. When: large tabular datasets, Kaggle-style competitions, when squeezing out maximum tabular accuracy matters.
  • SVM: finds the maximum-margin separating hyperplane (optionally using a kernel trick for non-linear boundaries). Strengths: effective in high dimensions, strong theoretical guarantees. Weaknesses: doesn't scale well to very large datasets, requires careful kernel/hyperparameter choice.
  • Naive Bayes: applies Bayes' theorem assuming features are conditionally independent given the class. Strengths: extremely fast, works surprisingly well for text classification despite the "naive" independence assumption. Weaknesses: the independence assumption is usually false, which can bias probability estimates (even when the final classification is still correct).

09 — Unsupervised Learning

Learning objectives

By the end of this topic you can: - Fit and compare K-means, hierarchical clustering, and DBSCAN. - Explain PCA and SVD as dimensionality reduction, and apply them before and after clustering. - Use t-SNE/UMAP for visualization and explain why they're for visualization, not general-purpose dimensionality reduction for downstream models.

Why it matters

Most real-world data has no labels. Clustering surfaces structure (customer segments, anomalies); dimensionality reduction makes high-dimensional data tractable to visualize, store, and feed to simpler downstream models — both are everyday tools, not just academic exercises.

Prerequisites

08_classification; Day 1's 05_ml_mathematics (eigenvectors/SVD, covered again here in an ML-algorithm context).

Core concepts

  • K-means: partitions data into k clusters by iteratively assigning points to the nearest centroid and recomputing centroids. Strengths: fast, simple. Weaknesses: must choose k in advance, assumes roughly spherical, similarly-sized clusters.
  • Hierarchical clustering: builds a tree (dendrogram) of nested clusters by repeatedly merging (agglomerative) the closest pair. Strengths: no need to pick k upfront, the dendrogram shows structure at every granularity. Weaknesses: O(n²) or worse, doesn't scale to very large datasets.
  • DBSCAN: density-based — groups points that are densely packed together, marking sparse points as noise/outliers. Strengths: finds arbitrarily shaped clusters, automatically detects outliers, no need to specify k. Weaknesses: sensitive to its two hyperparameters (eps, min_samples), struggles when clusters have very different densities.
  • PCA: projects data onto the directions (principal components) of maximum variance — a linear dimensionality reduction (covered mathematically in Day 1's 05_ml_mathematics).
  • SVD: the general matrix factorization PCA is built on; applies even to non-square, sparse matrices (e.g. recommender systems).
  • t-SNE / UMAP: non-linear techniques that preserve local neighborhood structure for 2D/3D visualization. They distort global distances and are not suitable as a general preprocessing step before a downstream supervised model (unlike PCA) — their primary use is making high-dimensional data visually inspectable.

10 — ML Optimization

Learning objectives

By the end of this topic you can: - Explain the relationship between a loss, an objective, and a cost function. - Implement and compare gradient descent variants: batch, SGD, mini-batch, momentum, AdaGrad, RMSProp, Adam, AdamW. - Explain learning-rate schedules, warmup, and decay, and why they matter in practice.

Why it matters

Every model in this curriculum — from linear regression to the Transformers in Day 3 — is fit by some variant of gradient descent. Knowing why Adam usually beats plain SGD, and why a learning rate schedule matters, is the difference between a training run that converges in an hour and one that never converges at all.

Prerequisites

07_regression (gradient descent from scratch) and Day 1's 05_ml_mathematics (the chain rule/gradient).

Core concepts

  • Loss / objective / cost: a loss is computed per-example; cost (or objective) is typically the average loss over a batch/dataset — terms are often used interchangeably in practice, but the per-example vs aggregate distinction matters when reasoning about gradients.
  • (Batch) Gradient descent: compute the gradient over the entire dataset before each update — accurate but slow per step, and may not fit in memory.
  • SGD (Stochastic Gradient Descent): update using the gradient from a single example — noisy but fast, and the noise can help escape shallow local minima.
  • Mini-batch SGD: the practical middle ground — update using a small batch (e.g. 32-256 examples); the de facto standard.
  • Momentum: accumulates a moving average of past gradients, smoothing out noisy updates and accelerating through consistent directions.
  • AdaGrad: adapts the learning rate per-parameter based on the sum of squared past gradients — shrinks the learning rate for frequently-updated parameters.
  • RMSProp: fixes AdaGrad's ever-shrinking learning rate by using an exponential moving average of squared gradients instead of a running sum.
  • Adam: combines momentum (first moment) and RMSProp-style adaptive per-parameter learning rates (second moment) — the most common default optimizer for deep learning.
  • AdamW: Adam with weight decay decoupled from the gradient update (rather than added into the gradient like L2 regularization) — generally preferred over plain Adam for training large models.
  • Learning-rate schedules, warmup, decay: starting with a small LR and ramping up (warmup) avoids early instability; decaying the LR over training helps fine-grained convergence near the end.
flowchart LR A[Full-batch GD: accurate, slow, memory-heavy] --> D[Mini-batch SGD: the practical default] B[Pure SGD: noisy, fast per-step] --> D D --> E[+ Momentum: smooths direction] E --> F[+ Adaptive LR: AdaGrad -> RMSProp] F --> G[Adam: momentum + adaptive LR] G --> H[AdamW: decoupled weight decay] H --> I[+ LR schedule: warmup then decay]

11 — Generalization

Learning objectives

By the end of this topic you can: - Formally define overfitting, underfitting, and the bias-variance tradeoff. - Apply L1, L2, and Elastic Net regularization and explain what each does differently. - Explain dropout and early stopping as regularization techniques, and why data augmentation helps.

Why it matters

06_ml_fundamentals introduced the underfit/overfit demo informally; this topic formalizes it and gives you the actual tools (regularization, early stopping) used to fix it in practice — tools you'll reuse directly on neural networks in Day 3.

Prerequisites

10_ml_optimization; the underfit/overfit demo in 06_ml_fundamentals.

Core concepts

  • Overfitting: the model fits training data (including its noise) so closely that it generalizes poorly to new data — low training error, high validation/test error.
  • Underfitting: the model is too simple to capture the underlying pattern — high error on both training and validation/test data.
  • Bias-variance tradeoff: bias = error from overly simplistic assumptions (underfitting); variance = error from sensitivity to the specific training sample (overfitting). Total expected error ≈ bias² + variance + irreducible noise — you can't drive both to zero simultaneously by adjusting capacity alone.
  • L1 regularization (Lasso): adds λΣ|w| to the loss — pushes some weights exactly to zero, giving automatic feature selection.
  • L2 regularization (Ridge): adds λΣw² to the loss — shrinks all weights smoothly toward zero without necessarily zeroing any out.
  • Elastic Net: a weighted combination of L1 and L2 — gets some sparsity (from L1) while keeping L2's smoother shrinkage.
  • Dropout (concept): randomly zeroes out a fraction of neurons during training, forcing the network to not rely on any single neuron — a regularization technique specific to neural networks (hands-on in Day 3).
  • Early stopping: stop training when validation loss stops improving, even if training loss keeps dropping — directly targets the overfitting point.
  • Data augmentation (concept): artificially expanding the effective training set (e.g. image flips/rotations, text paraphrasing) so the model sees more variation without needing more raw labeled data.
flowchart LR A[Model capacity too low] --> B[Underfitting: high bias] C[Model capacity too high, no regularization] --> D[Overfitting: high variance] E[L1/L2/Elastic Net] --> F[Shrink/zero weights -> reduce variance] G[Early stopping] --> F H[Data augmentation] --> F B -.opposite failure mode of.-> D F --> I[Better generalization: validation/test performance]

Important APIs / functions

Key takeaways

  • Bias and variance trade off against each other as capacity changes — regularization explicitly buys down variance at the cost of a little bias.
  • L1's sparsity (exact zeros) makes it useful for feature selection; L2's smooth shrinkage is usually better when all features are at least somewhat relevant.

12 — ML Evaluation

Learning objectives

By the end of this topic you can: - Build a confusion matrix and derive accuracy, precision, recall, F1, and specificity from it. - Explain ROC-AUC vs PR-AUC and when to prefer one over the other (especially under class imbalance). - Compute ranking metrics (Precision@K, Recall@K, MRR, MAP, NDCG) for recommendation/search-style problems. - Use cross-validation (including stratified K-fold) correctly, and recognize leakage in an evaluation setup.

Why it matters

A model is only as trustworthy as its evaluation. Every classifier in 08_classification was judged on accuracy alone, which is actively misleading on imbalanced data — this topic gives you the full toolkit real evaluation dashboards use, and the cross-validation discipline that prevents an optimistic, non-reproducible performance claim.

Prerequisites

11_generalization; 08_classification.

Core concepts

  • Confusion matrix: a table of (true label) × (predicted label) counts — the source of every classification metric below.
  • Accuracy: (TP+TN)/total — misleading under imbalance (a model that always predicts the majority class can have high accuracy).
  • Precision: TP/(TP+FP) — of everything predicted positive, how much was actually positive. Matters when false positives are costly.
  • Recall (sensitivity): TP/(TP+FN) — of everything actually positive, how much was caught. Matters when false negatives are costly.
  • Specificity: TN/(TN+FP) — the negative-class analog of recall.
  • F1: harmonic mean of precision and recall — a single number balancing both.
  • ROC-AUC: area under the ROC curve (TPR vs FPR across thresholds) — measures ranking quality independent of threshold, but can look optimistic under heavy class imbalance.
  • PR-AUC: area under the precision-recall curve — more informative than ROC-AUC when the positive class is rare.
  • Regression metrics recap: MAE/MSE/RMSE/R² (from 07_regression).
  • Ranking metrics: Precision@K/Recall@K (top-K relevance), MRR (mean reciprocal rank — how high the first relevant result ranks), MAP (mean average precision across ranks), NDCG (rewards relevant results ranked higher, with graded relevance).
  • Cross-validation / stratified K-fold: repeatedly splitting data into train/validation folds to get a more reliable performance estimate than a single split; stratified K-fold preserves class proportions in every fold — critical under imbalance.
  • Leakage (recap, now in an evaluation context): any evaluation setup where information from outside the current fold's training data influences that fold's score.

13 — Feature Engineering

Learning objectives

By the end of this topic you can: - Distinguish numerical and categorical features and apply the right encoding/scaling for each. - Handle missing values and outliers deliberately, not by default. - Perform feature selection and feature extraction, and explain the difference. - Build a leakage-safe Pipeline/ColumnTransformer that applies different preprocessing to different column types.

Why it matters

Feature engineering is where most of the practical performance gain in tabular ML comes from — more than algorithm choice, in many real projects. It's also where leakage (from 04_datasets/12_ml_evaluation) most often sneaks in, so this topic closes the loop by building everything inside a Pipeline.

Prerequisites

12_ml_evaluation (cross-validation, leakage, Pipeline-based correctness).

Core concepts

  • Numerical vs categorical features: continuous/ordered values vs discrete, unordered (or ordinal) categories — each needs different treatment.
  • Encoding: one-hot encoding (a column per category, for unordered/nominal categories) vs ordinal encoding (a single integer column, for genuinely ordered categories) vs target/mean encoding (encode a category by a statistic of the target — powerful but leakage-prone if not done inside cross-validation folds).
  • Scaling/normalization: StandardScaler (zero mean, unit variance) vs MinMaxScaler (bounded [0,1]) — matters for distance-based models (k-NN, SVM) and gradient-based optimization, not for tree-based models.
  • Missing values: SimpleImputer (mean/median/most-frequent) vs more sophisticated model-based imputation — the right choice depends on why data is missing (missing-at-random vs missing-not-at-random).
  • Outliers: cap (winsorize), remove, or transform (log) — the right choice depends on whether the outlier is a data error or a genuine extreme value.
  • Feature selection: choosing a subset of existing features (e.g. SelectKBest, L1-based selection from 11_generalization) — doesn't create new features, just prunes.
  • Feature extraction: deriving new features from existing ones (e.g. PCA components from 09_unsupervised_learning, polynomial features, domain-specific ratios/aggregates).
  • Pipelines: chaining preprocessing + model into one object so fit/predict/cross-validation apply every step consistently and leakage-safely (ColumnTransformer applies different preprocessing per column type within the same pipeline).

14 — Hyperparameter Tuning

Learning objectives

By the end of this topic you can: - Clearly separate parameters from hyperparameters (recap from 06_ml_fundamentals, now applied). - Use grid search and random search correctly, leakage-safely, with cross-validation. - Explain the intuition behind Bayesian optimization and why it can beat random search with fewer trials. - Combine early stopping with hyperparameter search, and compare experiments rigorously.

Why it matters

This topic is where everything from Day 2 comes together: regularization strength (11), feature-selection k (13), optimizer learning rate (10), and model-specific knobs (08) are all hyperparameters that need systematic tuning — not guesswork — using the leakage-safe Pipeline + cross-validation machinery from 12_ml_evaluation.

Prerequisites

13_feature_engineering (the Pipeline to tune) and 12_ml_evaluation (cross-validation).

Core concepts

  • Parameters vs hyperparameters (recap): parameters are learned by the optimizer during .fit(); hyperparameters are set before fitting and control how fitting happens.
  • Grid search: exhaustively try every combination of a specified hyperparameter grid — guaranteed to find the best combination within the grid, but scales exponentially with the number of hyperparameters.
  • Random search: sample random combinations from specified distributions — often finds a comparably good combination with far fewer trials than grid search, especially when only a few hyperparameters actually matter.
  • Bayesian optimization (concept): builds a probabilistic model of "hyperparameters → score" and uses it to choose the next most-promising point to try, rather than sampling blindly — more sample-efficient than random search, at the cost of being sequential (harder to parallelize).
  • Early stopping as part of tuning: combine a validation-based stopping rule (11_generalization) with a hyperparameter search so each trial doesn't need to run to a fixed, possibly wasteful budget.
  • Experiment comparison: comparing different hyperparameter configurations rigorously means comparing cross-validated score distributions (mean ± std across folds), not single numbers.
flowchart LR A[Hyperparameter search space] --> B[Grid search: exhaustive, exponential cost] A --> C[Random search: sampled, often comparably good, cheaper] A --> D[Bayesian optimization: model-guided, sample-efficient, sequential] B --> E[Cross-validated score per combination] C --> E D --> E E --> F[Pick the best by mean cross-val score, not a single fold]

Important APIs / functions

Key takeaways

  • Random search is usually "good enough" and dramatically cheaper than grid search once there are more than 2-3 hyperparameters to tune.
  • Bayesian optimization's advantage is sample efficiency, not necessarily final quality — with enough trials, random search often catches up.
  • Always compare hyperparameter configurations using cross-validated score distributions, not a single train/test split (connects directly back to 12_ml_evaluation).
  • Tuning hyperparameters on the test set (even implicitly, by repeatedly checking test performance) is itself a form of leakage — tune on validation/cross-validation, report final numbers on a held-out test set exactly once.

Common mistakes

  • Using grid search with a large hyperparameter grid, not realizing the combinatorial explosion (e.g. 5 hyperparameters × 5 values each = 3,125 combinations × CV folds).
  • Tuning hyperparameters by repeatedly checking test-set performance, which leaks test information into the final model choice.
  • Not using the same cross-validation splits across different search strategies, making "fair" comparisons invalid.
  • Forgetting that random search's budget (number of trials) is itself a parameter of the comparison — more trials generally means a better best-found score, independent of the search strategy's intrinsic quality.

15 — Deep Learning Fundamentals

Learning objectives

By the end of this topic you can: - Explain the perceptron and how stacking them into layers gives an MLP. - Implement a forward pass (weights, biases, activations) by hand with NumPy. - Explain and implement sigmoid, tanh, ReLU, Leaky ReLU, GELU, and softmax, and state why each exists. - Explain MSE, binary cross-entropy (BCE), and (categorical) cross-entropy as loss functions, and when to use each.

Why it matters

Every neural network — from a 2-layer MLP to a Transformer — is the same four ingredients repeated: weighted sums, activation functions, a loss function, and gradients. If the forward pass here is solid, Day 3's 16_backpropagation (the backward pass) and 18-22 (the same thing in PyTorch) will feel like syntax, not new concepts.

Prerequisites

Day 2's 10_ml_optimization (gradient descent) and Day 1's 05_ml_mathematics (matrix multiplication, the chain rule).

Core concepts

  • Perceptron: the simplest unit — a weighted sum of inputs plus a bias, passed through a step function. The historical ancestor of a neural network neuron.
  • Neural network / MLP (Multi-Layer Perceptron): perceptrons stacked in layers, with a non-linear activation between layers — without the non-linearity, stacking linear layers would collapse into a single linear layer.
  • Weights and biases: each layer is Y = XW + b, exactly the 07_regression linear-layer shape reasoning from Day 1/2, repeated per layer.
  • Forward pass: feeding an input through every layer in sequence to produce a prediction.
  • Loss: a single number measuring how wrong the prediction was — what the network is trained to minimize.
  • Backward pass (preview): computing how much each weight contributed to the loss — the subject of 16_backpropagation.
  • Activation functions:
  • Sigmoid: squashes to (0,1) — useful for binary probabilities, but saturates (near-zero gradient) for large |x|.
  • Tanh: squashes to (-1,1), zero-centered (often better-behaved than sigmoid), still saturates.
  • ReLU: max(0,x) — the modern default; cheap, doesn't saturate for positive inputs, but can "die" (always output 0) for inputs that are always negative.
  • Leaky ReLU: max(αx, x) for small α — fixes ReLU's dying-neuron problem by allowing a small negative slope.
  • GELU: a smooth approximation to ReLU using the Gaussian CDF — common in Transformers (e.g. GPT, BERT).
  • Softmax: converts a vector of raw scores ("logits") into a probability distribution that sums to 1 — used for multiclass output layers.
  • Loss functions:
  • MSE: for regression — squared difference between prediction and target.
  • BCE (Binary Cross-Entropy): for binary classification — penalizes confident wrong predictions heavily.
  • Cross-entropy: the multiclass generalization of BCE, paired with softmax output.

16 — Backpropagation

Learning objectives

By the end of this topic you can: - Trace the full training step: forward pass → prediction → loss → gradients → backward pass → optimizer → updated weights. - Compute every gradient for a tiny 2-layer network by hand, matching a numerical gradient check. - Explain why backpropagation is "just" the chain rule applied layer by layer, cached efficiently.

Why it matters

This is the single most important mechanism in all of deep learning, and the part most engineers treat as a black box. Doing it by hand once, on a tiny example, removes the mystery before PyTorch's autograd (19_pytorch_autograd) does it automatically — you'll be verifying autograd's output against your own hand-derived gradients, not trusting it blindly.

Prerequisites

15_deep_learning (the forward pass, losses) and Day 1's 05_ml_mathematics (the chain rule).

Core concepts

forward pass
→ prediction
→ loss
→ gradients (backward pass)
→ optimizer
→ updated weights
  • Forward pass: compute every layer's output, keeping the intermediate values (Z1, A1, Z2, ...) — they're needed again during the backward pass.
  • Loss: a single scalar, as in 15_deep_learning.
  • Backward pass: starting from the loss, apply the chain rule layer by layer, backward through the network, computing ∂Loss/∂W for every weight matrix and ∂Loss/∂b for every bias.
  • The key reuse: each layer's backward computation reuses the gradient computed one layer downstream (∂Loss/∂A_next) — this reuse, not any new math, is why backprop is efficient compared to recomputing each weight's gradient independently from scratch.
  • Optimizer step: once every gradient is known, any optimizer from Day 2's 10_ml_optimization (SGD, Adam, ...) can use them to update weights — backprop only computes the gradients, the optimizer decides how to use them.

17 — Deep Learning Architectures: CNN, RNN/LSTM/GRU, Attention, Transformer

Learning objectives

By the end of this topic you can: - Explain convolution, kernels, stride, padding, and pooling, and implement a 2D convolution from scratch. - Explain RNN/LSTM/GRU and why vanilla RNNs struggle with long sequences. - Explain query/key/value, self-attention, cross-attention, and multi-head attention — and implement scaled dot-product attention from scratch. - Describe the full Transformer block: embeddings, positional encoding, multi-head attention, FFN, residual connections, normalization, encoder/decoder, and causal masking.

Why it matters

This topic is the direct on-ramp to everything in this workspace's llm-fine-tuning/ curriculum — every LLM is a stack of Transformer blocks. Understanding why attention replaced RNNs (parallelizable, no vanishing-gradient-over-time problem) and what each piece of a Transformer block does is the difference between using Hugging Face models as a black box and actually understanding what you're fine-tuning.

Prerequisites

16_backpropagation (gradients through a network); Day 1's 02_numpy (shape reasoning, now applied to much higher-dimensional tensors).

Core concepts

CNNs

  • Convolution: slide a small learned filter (kernel) across the input, computing a dot product at each position — detects local patterns (edges, textures) regardless of position.
  • Stride: how far the kernel moves per step — larger stride = smaller output, less overlap.
  • Padding: adding border pixels (usually zeros) so the output size can match the input size ("same" padding) instead of always shrinking ("valid" padding).
  • Pooling: downsampling (e.g. max pooling) — reduces spatial size and adds translation invariance.

RNNs

  • RNN: processes a sequence step by step, carrying a hidden state forward — in principle captures arbitrary-length context, but vanishing/exploding gradients over many steps make long-range dependencies hard to learn.
  • LSTM / GRU: add gating mechanisms (forget/input/output gates for LSTM; reset/update gates for GRU) specifically to control what the hidden state remembers vs forgets, mitigating vanishing gradients — GRU is a simpler, often similarly effective variant of LSTM.

Attention and Transformers

  • Query/Key/Value: for each position, compute a query ("what am I looking for"), compared against every position's key ("what do I offer") to get attention weights, which weight every position's value ("what information do I carry").
  • Self-attention: queries, keys, and values all come from the same sequence — every token can directly attend to every other token, in one step (unlike an RNN's step-by-step propagation).
  • Cross-attention: queries come from one sequence, keys/values from another (e.g. decoder attending to encoder outputs in a translation model).
  • Multi-head attention: run several attention computations ("heads") in parallel, each potentially learning a different kind of relationship, then combine the results.
  • Transformer block: embeddings → (+ positional encoding, since attention has no inherent sense of order) → multi-head self-attention → residual connection + normalization → feed-forward network (FFN) → another residual connection + normalization.
  • Encoder/decoder: an encoder processes the full input at once (bidirectional attention); a decoder generates output step by step and uses causal masking to prevent attending to future tokens it hasn't generated yet.
  • Residual connections: output = x + f(x) — lets gradients flow directly through many stacked layers, critical for training very deep networks.
  • Normalization (LayerNorm): normalizes activations within each sample, stabilizing training in deep stacks of layers.

19 — PyTorch Autograd

Learning objectives

By the end of this topic you can: - Explain the computational graph PyTorch builds when requires_grad=True. - Use .backward() and .grad to compute gradients automatically, and verify them against 16_backpropagation's hand-derived gradients. - Explain torch.no_grad() and when/why to use it.

Why it matters

This is the payoff for 16_backpropagation. Every gradient computed by hand there is computed automatically here — the exact same math, just tracked by a graph instead of derived on paper. Trusting (and knowing how to debug) autograd is foundational to every PyTorch training loop from here on.

Prerequisites

18_pytorch_basics (tensors) and 16_backpropagation (the chain rule, done by hand — this topic automates exactly that).

Core concepts

  • Computational graph: as operations are performed on tensors with requires_grad=True, PyTorch records them in a graph connecting inputs to outputs — this graph is what .backward() walks in reverse.
  • requires_grad: marks a tensor as one PyTorch should track operations on, for later gradient computation. Model parameters have this set automatically; raw input data usually doesn't need it.
  • .grad: after .backward(), each leaf tensor with requires_grad=True has its computed gradient accumulated here — note "accumulated," not "overwritten" (.grad.zero_() between steps matters, previewed here, used for real in 22_pytorch_training).
  • .backward(): triggers the automatic backward pass over the computational graph, computing ∂output/∂input for every tracked tensor.
  • Chain rule (recap): autograd's internal mechanism is exactly 16_backpropagation's chain rule, applied automatically to an arbitrary graph of operations instead of a fixed 2-layer MLP derived by hand.
  • torch.no_grad(): a context manager that disables gradient tracking — used during inference/evaluation, where gradients are never needed and tracking them wastes memory and compute.

Why it matters

nn.Module is the organizing unit of every PyTorch model, from a 2-layer MLP to a full LLM. It automatically registers parameters (so an optimizer can find them) and gives every model a consistent forward() interface — this is the structure 22_pytorch_training's training loop expects.

Prerequisites

19_pytorch_autograd (the gradients this wraps) and 17_deep_learning_architectures (the architecture being rebuilt as a module).

Core concepts

  • nn.Module: the base class for all PyTorch models/layers. Subclass it, define sub-layers in __init__, and implement forward() — calling the module (model(x)) invokes forward() automatically and handles bookkeeping.
  • nn.Linear: a fully-connected layer (Y = XW^T + b) — replaces manually tracking W/b tensors from 19_pytorch_autograd, and registers its weights as parameters automatically.
  • nn.Embedding: a lookup table mapping integer token IDs to dense vectors — the first layer of almost every NLP/LLM model.
  • nn.ReLU / nn.GELU: activation functions as modules (vs. the functional torch.relu used directly in 19_pytorch_autograd) — useful for putting activations inside nn.Sequential.
  • nn.LayerNorm: the production version of 17_deep_learning_architectures's from-scratch layer_norm function.
  • nn.Dropout: randomly zeroes elements during training (recap from Day 2's 11_generalization) — automatically disabled during .eval() mode.
  • nn.Softmax: softmax as a module, for use inside a forward() method or nn.Sequential.
  • Parameters: every nn.Linear/nn.Embedding/etc. registers its weights as nn.Parameters automatically — model.parameters() yields every learnable tensor in the whole module tree, which is exactly what an optimizer needs.

21 — PyTorch Data: `Dataset` and `DataLoader`

Learning objectives

By the end of this topic you can: - Implement a custom Dataset (__len__ + __getitem__) and an IterableDataset for streaming data. - Use DataLoader correctly: batching, shuffling, num_workers, pin_memory, and a custom collate_fn. - Explain why num_workers uses separate processes, connecting back to Day 1's GIL discussion.

Why it matters

Every PyTorch training loop pulls batches from a DataLoader. Getting this right (correct batching, efficient parallel loading, proper shuffling) is often the difference between a GPU sitting idle waiting for data and one running at full utilization.

Prerequisites

20_pytorch_models; Day 1's 01_python (the ToyDataset class with __len__/__getitem__ was literally a Dataset preview) and 04_datasets (Hugging Face datasets, a different but related abstraction).

Core concepts

  • Dataset: an object implementing __len__ and __getitem__ — exactly the magic-method contract previewed with ToyDataset in Day 1's 01_python. Represents the whole dataset, accessible by index.
  • IterableDataset: implements __iter__ instead — for data that's naturally streamed (too large to index randomly, or generated on the fly) rather than indexed, mirroring Day 1's 04_datasets streaming IterableDataset from Hugging Face.
  • DataLoader: wraps a Dataset, handling batching, shuffling, and parallel loading — this is what a training loop actually iterates over.
  • Batching: grouping multiple samples into one tensor per step — DataLoader's default collate_fn stacks same-shaped samples automatically.
  • Shuffle: randomizing sample order each epoch — essential for SGD-based training (connects to Day 2's 10_ml_optimization) to avoid learning spurious patterns from data order.
  • num_workers: spawns separate processes (not threads) to load/preprocess data in parallel while the GPU/CPU trains on the previous batch — separate processes specifically because of the GIL (Day 1's 01_python), the same reason multiprocessing was needed there for CPU-bound work.
  • pin_memory: allocates batches in page-locked memory, speeding up the CPU→GPU transfer (relevant when training on CUDA).
  • collate_fn: a custom function controlling how a list of samples becomes a batch — needed when samples have variable-length data (e.g. different-length token sequences) that can't be stacked by default.

23 — PyTorch Performance

Learning objectives

By the end of this topic you can: - Explain FP32 vs FP16 vs BF16 and what mixed precision training trades off. - Implement gradient accumulation (simulating a larger batch size than fits in memory) and gradient clipping (preventing exploding gradients). - Identify data-loading bottlenecks and use basic profiling to find them. - Explain GPU memory considerations at a level sufficient to reason about batch size and model size tradeoffs.

Why it matters

This is where "my model trains correctly" becomes "my model trains fast enough, and fits in memory, on the hardware I actually have." Every one of these techniques (mixed precision, gradient accumulation, clipping) is standard practice in this workspace's llm-fine-tuning/ curriculum, where models are large enough that naive full-precision, full-batch training simply doesn't fit.

Prerequisites

22_pytorch_training (the pipeline being optimized).

Core concepts

  • CPU vs GPU: GPUs offer massive parallelism for matrix multiplication (the core cost of deep learning) but have their own (usually smaller) memory, and data must be explicitly moved there (18_pytorch_basics's .to(device)).
  • GPU memory: bounded by the GPU's VRAM; must hold the model's parameters, gradients, optimizer state (e.g. Adam keeps two extra moment buffers per parameter), and activations for the current batch — this is why larger models or batch sizes can run out of memory even when compute would be fast enough.
  • FP32 / FP16 / BF16: FP32 (32-bit float) is the default; FP16 (16-bit) and BF16 (16-bit, different exponent/mantissa split) use half the memory and are faster on modern GPUs, at the cost of reduced numeric range/precision — BF16 keeps FP32's exponent range (more stable) while sacrificing mantissa precision, making it generally preferred over FP16 for training stability.
  • Mixed precision: run most operations in FP16/BF16 for speed/memory, but keep certain numerically sensitive operations (e.g. loss scaling, some reductions) in FP32 — PyTorch's torch.autocast + GradScaler (for FP16) automate this.
  • Gradient accumulation: simulate a larger effective batch size than fits in memory by accumulating gradients over several smaller "micro-batches" before calling optimizer.step().
  • Gradient clipping: cap the gradient's norm before the optimizer step, preventing a single bad batch from causing an exploding-gradient update (connects to 17_deep_learning_architectures's RNN vanishing/exploding gradient discussion).
  • Data-loading bottlenecks: if the GPU finishes a batch faster than the DataLoader (recap from 21_pytorch_data) can produce the next one, the GPU sits idle — profiling reveals this.
  • Profiling: measuring where time is actually spent (data loading vs forward vs backward vs optimizer step) before trying to optimize blindly.
flowchart LR A[FP32 default] --> B[FP16/BF16: half memory, faster on modern GPUs] B --> C[Mixed precision: autocast + loss scaling] D[Batch too large for memory] --> E[Gradient accumulation: micro-batches, fewer optimizer steps] F[Unstable/exploding gradients] --> G[Gradient clipping: cap gradient norm] H[GPU idle between batches] --> I[Profile: is the bottleneck data loading or compute?]

Core concepts

  • Tokenizer: converts raw text into a sequence of integer token IDs a model can consume — using a fixed, pretrained vocabulary specific to that model.
  • Token IDs: the integers a tokenizer produces; each corresponds to a row in the model's nn.Embedding table (20_pytorch_models) that turns it into a dense vector.
  • Attention mask: a binary mask marking which tokens are real content vs padding (recap from 21_pytorch_data's variable-length collate_fn) — padded positions are masked out of attention (17_deep_learning_architectures) so they don't influence the output.
  • AutoTokenizer / AutoModel / AutoModelForCausalLM: Hugging Face's "Auto" classes inspect a model's config and load the right tokenizer/model class automatically — you rarely need to know the exact underlying class name.
  • generate(): a high-level method handling the full autoregressive generation loop (recap: causal masking from 17_deep_learning_architectures) — repeatedly predicting the next token and feeding it back in, so you don't have to write that loop by hand.
  • Model configuration: hyperparameters baked into a pretrained model (number of layers, hidden size, number of attention heads — all vocabulary from 17_deep_learning_architectures) stored in a config object/file alongside the weights.
  • Dataset preprocessing (recap): tokenizing a Hugging Face datasets.Dataset (Day 1's 04_datasets) via .map(tokenizer_fn, batched=True) is the standard way to prepare text data for a model.
  • PEFT / LoRA (concept only): fine-tuning every parameter of a large pretrained model is expensive; PEFT (Parameter-Efficient Fine-Tuning) methods like LoRA (Low-Rank Adaptation) freeze the original weights and train a small number of additional low-rank parameters instead — dramatically cheaper, while often nearly matching full fine-tuning quality. This is introduced only at a concept level here — full hands-on LoRA/QLoRA is this workspace's llm-fine-tuning/02_lora_qlora_peft.

Key takeaways

  • A tokenizer's vocabulary is tied to the specific pretrained model — using the wrong tokenizer for a model produces garbage, silently.
  • generate() is doing the exact autoregressive loop (causal masking, repeated next-token prediction) covered conceptually in 17_deep_learning_architectures — it's not new theory, just a convenient wrapper.
  • LoRA's core insight — most of the change needed to adapt a model to a new task lives in a low-rank subspace — is why it can train a tiny fraction of the parameters and still work well; this curriculum stops at the concept, and llm-fine-tuning/02_lora_qlora_peft in this workspace goes hands-on.

Common mistakes

  • Mixing a tokenizer from one model with weights from a different model.
  • Forgetting the attention mask when batching variable-length sequences, letting padding tokens leak into attention (connects directly to 21_pytorch_data's collate function and 17_deep_learning_architectures's masking).
  • Treating generate()'s default settings (e.g. greedy decoding) as the only option without being aware sampling strategies exist (out of scope here — covered in llm-fine-tuning/).
  • Downloading a large model "just to try it" instead of starting with a small CPU-friendly one for learning purposes.
